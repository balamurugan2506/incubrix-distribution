The problem
IncuBrix Distribution already publishes to the 15 major platforms (YouTube, Instagram, Facebook, LinkedIn, TikTok, X,
Threads, Pinterest, Bluesky, Mastodon, Reddit, Vimeo, WordPress, Telegram and Discord) and to RSS feeds. These

communities where automated posting is not allowed and a person must post. There are hundreds of these, each with
its own format limits and its own rules. One careless post can get IncuBrix banned from a community.

The key idea: one connector, many destinations
A destination is one place that reaches one audience: one forum, one community, one newsletter. A connector is the
code for one kind of platform. One Discourse connector must serve every Discourse forum, so adding forum number 41
should be a single configuration row, not new code. And no destination counts until it is certified: its format limits and
posting rules are recorded and a real test post has succeeded and been cleaned up.
Out of scope
The 15 major platforms and RSS (already live); paid boosting and ads; lead generation; cold email and outreach; billing.
What you build
1. Connectors that follow the IncuBrix connector contract exactly (Appendix A): the same methods, manifest format and
error codes as our existing connectors, so our runtime can load them unchanged.
2. Posting-rules engine: each destination's rules (how often we may post, whether self-promotion is allowed, link rules,
AI-disclosure rules) are stored and checked before every post.
3. Certification harness: for each destination, publish a test post, confirm it is live, read its status and delete it (or post to
an agreed sandbox), and store the evidence.
4. Destination catalogue tools (Advanced): import a spreadsheet of destinations, clean it, score each one for relevance
to IncuBrix's audience, and capture its rules.
5. Tailoring and recommendation (Advanced and Outstanding): adapt the title, text and format for each destination, and
recommend where a piece of content should go.
IncuBrix's audience for relevance scoring: AI, video, marketing, SaaS, creators and founders.

How it must plug into IncuBrix (Integration Standard)
IncuBrix runs its services as containers that talk to each other over HTTP APIs. If your submission follows the ten points
below, we can connect it to the product without rewriting it. Each point is worth 2 marks (20 marks in total). Tick each
one in your Submission Form with a link to the proof.
Requirement
What exactly we check
1. One-command start
and test
docker compose up starts the service and everything it needs (database, storage, local test
servers). One command runs all tests (unit, integration and at least one end-to-end) with no API keys.
A .env.example lists every setting.
2. Documented HTTP
API
An openapi.yaml (OpenAPI 3.1) that matches the running service exactly. All routes under
/api/v1/.
3. Background jobs
Anything slower than 2 seconds runs as a job: POST returns 202 with a job_id; GET
/api/v1/jobs/{job_id} returns status (queued, running, succeeded, failed), progress 0-100 and
result links. Optional callback URL, signed with HMAC-SHA256 in an X-IncuBrix-Signature
header.
4. Safe retries
An Idempotency-Key header on every POST: sending the same request twice with the same key
returns the same job and never does the work twice.
5. Clear errors
Errors are JSON: {"error": {"code", "message", "retryable", "details"}}. Codes
are UPPER_SNAKE_CASE and listed in the README.
6. Configuration
All settings, paths, model names and limits come from environment variables or a config file. No
hard-coded paths or keys.
7. Files in, files out
Inputs accepted as an upload or a URL. Outputs saved to S3-compatible storage (MinIO in the
compose file is fine) and returned as download links.
8. Logs and health
Structured JSON logs with timestamp, level, job_id and the X-Correlation-Id from the request.
GET /health and GET /ready endpoints.
9. Output manifest
Every result includes a JSON manifest: which models/providers and versions were used, settings,
seed, timings, cost estimate, warnings, and licence/rights information.
10. Batch runner
A command-line tool that runs a folder or file of test inputs against the API and writes all results to one
folder. We use this to test every submission the same way.
Tools and resources: use anything
We want to see the best system you can build, the way you would build it at work. There are no restrictions on tools.
  AI coding assistants (ChatGPT, Claude, Copilot, Cursor and so on): allowed, as much as you like.
 Any AI model or service: open-source or proprietary, self-hosted or hosted API, free or paid.
 Any compute: your laptop, a cloud GPU, a free notebook, a paid server.
 Any open-source code or library, as long as you credit it and its licence allows commercial use.
Because your solution should be able to go straight into the IncuBrix product, five rules apply:
1. Disclose everything. List every model, API, library, dataset and media source in SOURCES.md, and every AI coding
tool you used (and for what) in AI_USE.md.
2. Commercially usable. Everything in your default path, and everything it outputs, must be licensed for commercial use.
No research-only or non-commercial models, data or media (for example CC BY-NC) in the default path. Avoid AGPL
code in the shipped service.
3. Swappable providers. Put every external AI service behind a small adapter selected by configuration, and include a
mock adapter so tests run with no API keys.
4. Know your cost. Report the cost and time per unit of output (for example per minute of video). Paid services are fine,
but you will not get extra marks for spending more. IncuBrix does not reimburse costs unless agreed in writing before
you spend.
5. No secrets in the code. API keys live in environment variables or a secret store, never in the repository, logs or
screenshots.

Appendix A: the IncuBrix connector contract
Write connectors in Python 3.11+ or TypeScript (Node 20+). Expose each method over HTTP at POST
/connector/v1/{connector_key}/{method} with JSON bodies, so our Connector Runtime can call them
whatever language you choose.
Methods
 validate(rendition, destination, connection)            -> {ok, violations[]}
publish(rendition, destination, connection, idempotency_key)
                                                        -> {platform_post_id, live_url, status}
get_status(platform_post_id, connection)                -> {status, live_url}
delete(platform_post_id, connection)                    -> {deleted}
fetch_metrics(platform_post_id, connection, since)      -> {views, likes, comments, shares,
                                                            saves, watch_time_s, clicks}   # optional
refresh_auth(connection)                                -> {expires_at}                    # optional
build_assist_pack(rendition, destination)               -> {files[], caption, deep_link,
                                                            checklist[]}          # assisted tier only
Methods return results only. They never write to IncuBrix's database; our runtime does that.
Manifest (one YAML file per connector)
 key: discourse
version: 1.0.0
tier: native            # native | protocol | bridge | feed | assisted
auth: api_key           # oauth2 | api_key | bot_token | none
surfaces:
  - key: topic
    content_types: [text, image, video_link]
    spec: {title_max_chars: 255, body_max_chars: 32000, links_allowed: true}
rate_limits:
  per_connection: {requests: 60, per_seconds: 60}
capabilities: [publish, status, delete, metrics]
error_map:
  "429": PLATFORM_RATE_LIMIT
  "422": PLATFORM_CONTENT_REJECTED
  "401": CONNECTION_AUTH_EXPIRED
instance_param: base_url   # one connector, many destinations (one per forum)
